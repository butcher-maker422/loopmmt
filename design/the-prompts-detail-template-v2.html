Burn It Down and See If You End Up Here Again

The Total Reframe Protocol

The most honest question you can ask about any solution:

The Prompt

I want a total reframe — RCR this, three times, running the framing protocol each time, new shuffle each time. Start over — what is actually the best product, given all we know? If you happen back upon the current model from a new starting position with the current conditions, we'll know it was right. RCR on this real quick — is this a good general protocol to run on ANY last-minute big decision? Look at the solution you just worked hard on, then throw it out of your mind and rebuild with all you know, without any of the weight of previous work. If you end up back in the same spot, or close to it, it's a good model check. If not, the results are most certainly bound to be productive, at the cost of time and tokens, which is fine. It's not something we could call on any decision, but maybe a good one for a big one, right at the end? RCR on the concept first, then if you think it's good, talk about how to build the protocol, then build it, if you decide it was the right call. Then run it, getting back to the start of my message with the three-stage RCR reframing, carried out by your newly built protocol.

— Shea Gunther · Instar 2 (Loop World)

The Moment

This is Session 2 — the second session of the entire project. The system that would become Loop MMT was barely a sketch: a handful of ideas about structuring AI-assisted development, tested across one prior session, carrying approximately zero infrastructure. No board. No protocols-in-force registry. No knowledge packs. Just an operator and a Claude instance, two sessions in, already asking the question that would define the system's relationship with its own conclusions.

The operator had built something in Session 1. Instead of iterating on it, he proposed destroying it — wiping the slate and rebuilding from the same knowledge base without the gravitational pull of the existing solution. If the rebuild converged, the model was validated, not by argument but by independent reconstruction. If it diverged, the divergence was itself the finding.

Wes — chaosTwo sessions in, the instinct was already don't trust your first answer. Most systems learn that late, if ever. This one was born knowing it.

The Anatomy

"Throw it out of your mind and rebuild with all you know, without any of the weight of previous work" — the operator is asking the instance to de-anchor: carry the knowledge forward but not the conclusion. It is the cognitive equivalent of asking someone to forget a melody while remembering the key it was played in.

"It's not something we could call on any decision, but maybe a good one for a big one, right at the end" — the constraint is deployed early and deliberately. The reframe is expensive; it costs time, tokens, and cognitive energy, so it is reserved for decisions where the cost of being wrong exceeds the cost of triple-checking. That cost-benefit test would later become a formal property of the Parallax protocol.

"RCR on the concept first… then build it… Then run it" — the final instruction is a meta-sequence: evaluate the concept, design the protocol, build it, then immediately use it to do the work that prompted its creation. The protocol is conceived, born, and put to work in the same session — a build-then-deploy pattern that would recur throughout the system's history.

Terms for the Outside Reader
RCR
Round · Collision · Resolution — the board's structured deliberation protocol. To "RCR" something is to argue it through to a decision.
De-anchor
Set aside your prior conclusion while keeping what you learned, so a rebuild isn't just a defense of the first answer.
Parallax
The confidence check this prompt became — shift the viewpoint, rebuild from scratch, and see whether you land in the same place.
