Make Sure All The Little Details Sparkle

The Whole Ceiling Drive, In One Sentence

A full build commission with its own process scaffold baked in:

The Prompt

Ed! I want to create a new game- I want to create Loop Sudoku!

Jamie is a Sudoku pro. I am decent. She plays just about every day, while I went through a brief phase last year where I played every day and made most of my way through a Sudoku teaching website. I tapped out at the very highest levels.

Anyway, I want to create Loop Sudoku, in that I want it to be able to exist either alone as a stand alone app OR as a part of the Loop MMT Ecosystem. So it will need all the hooks and whatnot that are involved with that.

I would like this to be good- not just bog standard Sudoku app, but something that is beautiful and elegant and enjoyable to touch and use. I don't want to try to radically engineer anything here- it's just Sudoku after all, but I do want to look to put our special crafty touch anywhere we can- make sure all the little details sparkle, you know?

I want to build this using our new system for Projects and Campaigns. Do you think this is a Project or a Campaign? Feels like just a Project, but let me know if you disagree.

It needs to be fully folded into and integrated with the rest of the App ecosystem and fit all our coding standards and what not. So we are going to have to build a canonical blueprint for it, from which we will make the golden example, is it the plumb? I forget the naming there. Then we will want to build the first working instance of it as part of my forest, which is in development. You should look that up so you can fold into that line properly. I want it to be a choosable tab on my new forest.

Players should be able to save and store their progress. We will roll more features out as we build, so keep that in mind from the start- it'll be nice someday to maybe have some kind of multiplayer collaboration, or different game types, or score and results sharing, or maybe even board creation, saving, and sharing.

One thing we need to do as part of this work is to learn EVERYTHING about Sudoku that there is to know on the internet. Load up HEAVY *X, math and science in particular, when doing this work, as well as a proper Kaleidoscope. Then fold in a bunch of other weird shit so we are building our understanding of Sudoko through all kinds of frames and lenses. This feels like, like the Game of Life, that there are probably a lot of interesting overlaps with Sudoku and all kinds of weird off-domain things. If we are going to have Loop Sudoku, Loop MMT needs to be as good as Sudoku as we can get you. As part of your work here, think about if we need to add any KPs to our KP collection. Also look into our Maths in Force and Math Atlas systems. For that matter, load up heavy with SX too so you know what internal tools we have available- we're designing, so you should be maybe using the Five Lenses? Also think in Blocks and Block^N and Block^3 and 8X. And we will certainly want to use our Gold Wash system to build with blocks we have already figured out.

And as always, I want Wes to bookend this whole thing- inject the right amount of FWW(C) in the beginning and then, at a minimum, check in at the end to make sure the right amount survived the build process in the right places.

Do this- start off with an RCR just organizing your thoughts on this whole thing- I want Chen Wei and Wren on lead here for the first one.

After that RCR, I want you to run the Kindling program to actually develop the first version plan for how we attack this- I want the plan to focus on the details of how we will actually carry this out- it's not to focus on how the actual solution is built, but rather on how we actually build that solution. So it needs to hone in on the process and the tools that we will use in order to find this solution shape- things like, is it a project or a campaign? If so, what do those particular structures, and their sub-structures, look like? What is the build process like? What kind of high level mile stones are we looking to place on the development timeline? I want to really work this one well, so think process. Roll in my Great Thinkers lens so you can be brutally pragmatic about designing something we can actually build.

Do NOT compress or blackbox and make sure you actually look up how to properly run an RCR.

— Shea Gunther

The Moment

Not every prompt reaches for something grand. This one asks for Sudoku — "it's just Sudoku after all" — and then refuses to let it be ordinary. The operator wants a game his fiancée, a daily player, would actually enjoy: beautiful, elegant, good to touch. The ambition is not in the mechanic; it is in the finish. And the requirement that it run both as a standalone app and as a citizen of the wider ecosystem quietly makes it a real architecture problem — one core, expressed two ways.

What makes this the maximal operator prompt is what comes after the opening: a full scaffold for how the work should be done — which reviews and lenses to load before building, who should lead the opening deliberation, and, pointedly, what not to do. The operator does not just commission the artifact; he specifies the process that should produce it. The captured opening sets the taste; the remainder sets the method.

The wider frame"Make all the little details sparkle" is the whole quality drive of the methodology in one operator sentence.

The Anatomy

"either alone as a stand alone app OR as a part of the Loop MMT Ecosystem. So it will need all the hooks and whatnot" — a one-line architecture requirement disguised as an aside. "Runs alone or as part of the whole" is the dual-expression pattern: a single shared core with two shells around it. The casual "hooks and whatnot" names a real integration surface the build had to honor.

"I don't want to try to radically engineer anything here- it's just Sudoku after all" — the constraint against over-engineering is deliberate. The instruction is to spend the craft on finish, not on novelty; to resist the pull to reinvent the game and instead make an ordinary game feel cared-for.

"put our special crafty touch anywhere we can- make sure all the little details sparkle, you know?" — the actual specification is a standard of care, not a feature list. "Sparkle" is unmeasurable and completely clear: every small interaction should feel considered. That drive toward finish — the Ceiling — is stated here more plainly than any protocol states it.

Reading the Operator’s Shorthand

The real prompt carries the working vocabulary of the methodology it was typed into. Here is what those terms mean, for a reader coming from outside it.

loop-sudoku
The game this prompt commissioned — built to run both on its own and inside the Loop MMT ecosystem, from a single shared core.
The Loop MMT Ecosystem / “my forest”
The wider set of apps the methodology has built, and the operator’s own self-hosted home for them — the “Forest” — where loop-sudoku is meant to live as a tab.
The Ceiling / FWW(C)
The methodology’s drive toward finish, polish, and enjoyment — the impulse this prompt names as making “all the little details sparkle.”
*X / KX / CX / SX / SWX
A family of “load up the right material before you start” reflexes — pulling in relevant knowledge, prior context, the available internal tools, and any already-built software worth reusing.
Gold Wash
The system for building out of parts already figured out, rather than re-solving what has been solved before.
Five Lenses
A design instrument — five ordered ways of looking at something being designed, run in sequence.
Blocks / Blockᴺ / Block³ / 8X
A composition language: name the parts, specify how they join, and build by combining known pieces — at several scales.
Kaleidoscope
A technique for assembling many vantage points on a problem at once, so it gets seen from more than one direction.
The Kindling program
A guided routine for developing the first version of a build plan — focused on how the work will be carried out, not on the solution itself.
Maths in Force / Math Atlas
The methodology’s registries of the formal results it relies on, and its map of equations to where they show up in the world.
Projects and Campaigns
The system’s two ways of structuring a piece of work — the prompt asks which shape loop-sudoku should take.
The blueprint / golden example / “the plumb”
The reference version of a tool — the canonical spec, and the first correct instance built from it that everything later is checked against.
RCR
A structured round of deliberation across the advisory board before a decision is taken.
Chen Wei / Wren / Wes
Members of the advisory board, named here to lead or bookend particular parts of the work.
